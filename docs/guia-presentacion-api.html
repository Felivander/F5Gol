API Laravel + Sanctumpuerto 8000 · acá vive Swagger

MySQLbase f5gol
  • Front y back son dos programas distintos, por eso tienen distinto puerto. La página no tiene datos propios: se los pide a la API.
  • Swagger documenta la API, así que vive en el back. Se genera solo, a partir de atributos #[OA\...] escritos arriba de cada método de los controladores.
  • Sanctum es el sistema de Laravel que genera el token en el login y lo controla en cada pedido protegido.

Guion de la demo

1. Qué es Swagger · 1 min

  1. Mostrá el título API F5Gol 1.0.0 y la descripción.

    “Esta es la documentación de nuestra API. Se genera automáticamente desde el código, así que siempre está al día.”

  2. Tocá el link api-docs.json debajo del título.

    “Esto es el archivo OpenAPI: un formato estándar que entienden muchas herramientas, no solo Swagger.”

  3. Volvé atrás y mostrá Servers: http://127.0.0.1:8000, servidor local.

2. Cómo está organizada · 1 min

  1. Bajá por los grupos: Autenticación, Canchas, Clubes, Jugadores anotados, Reservas, Turnos.
  2. Señalá los colores de cada método: GET leer · POST crear · PUT editar · DELETE borrar.
  3. Mostrá el candado a la derecha de los POST, PUT y DELETE.

    “Cualquiera puede consultar clubes, canchas y turnos, pero para crear, editar o borrar hay que iniciar sesión.”

3. Una lectura pública · 2 min

  1. Clubes → GET /api/clubs → Try it out → Execute.
  2. Explicá la respuesta: código 200, la lista en data y los datos de paginación (current_page, last_page, total).

    “La lista viene paginada de a 10, para no traer todo de golpe.”

  3. Turnos → GET /api/turnos → Try it out, con cancha_id = 1 y fecha = 2026-09-04. Execute.

    “Esta es la grilla de disponibilidad: cada turno tiene su estado y cuántos jugadores ya se anotaron.”

  4. Clubes → GET /api/clubs/{id} con 999. Devuelve 404.

    “Si algo no existe, la API lo dice con el código correcto.”

4. La seguridad · 2 min

  1. Clubes → POST /api/clubs → Try it out → Execute, todavía sin iniciar sesión.
  2. Mostrá el 401 con el mensaje: "No autenticado. Iniciá sesión y mandá el token en el encabezado Authorization."

    “Swagger muestra el candado, pero quien bloquea de verdad es Laravel: las rutas de escritura tienen el middleware auth:sanctum.”

5. Login y Authorize · 2 min

  1. Autenticación → POST /api/login → Try it out. El cuerpo ya trae el usuario de prueba: 
    {
  "email": "admin1@f5gol.com",
  "password": "password"
}
  2. Execute. Mostrá la respuesta: access_token y token_type: "Bearer". Copiá el token completo, con el número y la barra (por ejemplo 5|AbC...).
  3. Arriba a la derecha tocá Authorize, pegá el token y tocá Authorize otra vez. Cerrá el cuadro.

    “Desde ahora Swagger manda el token en cada pedido, en el encabezado Authorization: Bearer ....”

  4. Autenticación → GET /api/user → Execute. Devuelve el usuario logueado.

6. Crear un club · 1 min

  1. Clubes → POST /api/clubs → Try it out. Pegá este cuerpo: 
    {
  "administrador_id": 1,
  "nombre": "Club de la presentación",
  "direccion": "Av. Siempre Viva 742",
  "telefono": "3454000000"
}
    Execute: devuelve 201 con "message": "Club creado correctamente" y el club. Anotá el id: lo usás en los pasos que siguen.

7. Editar un dato y mandarlo · 1 min

  1. Clubes → PUT /api/clubs/{id} → Try it out. En id poné el del club que creaste.
  2. En el cuerpo mandá solo el campo que querés cambiar: 
    {
  "nombre": "Club de la presentación (editado)"
}
  3. Execute. Devuelve 200 con "message": "Club actualizado correctamente" y el club con el nombre nuevo.

    “Al editar no hace falta mandar todo: solo se validan y se guardan los campos que vienen en el pedido.”

  4. Para comprobarlo: GET /api/clubs/{id} con el mismo id muestra el nombre cambiado.

8. Mandar un dato erróneo y leer el mensaje · 2 min

  1. Mismo PUT /api/clubs/{id}, ahora con el nombre vacío: 
    {
  "nombre": ""
}
    Execute. Respuesta: código 422 y este cuerpo: 
    {
  "message": "El campo nombre es obligatorio.",
  "errors": {
    "nombre": ["El campo nombre es obligatorio."]
  }
}

    “422 significa que el pedido llegó bien pero los datos no son válidos. En errors viene un mensaje por cada campo con problema, para que el front lo pueda mostrar al lado del campo.”

  2. Varios errores juntos: un administrador que no existe y un teléfono que no es texto. 
    {
  "administrador_id": 999,
  "telefono": 12345
}
    Respuesta 422: 
    {
  "message": "El administrador indicado no existe. (y 1 error más)",
  "errors": {
    "administrador_id": ["El administrador indicado no existe."],
    "telefono": ["El campo teléfono tiene que ser un texto."]
  }
}
  3. Un texto demasiado largo: "nombre" con más de 150 caracteres da "El campo nombre supera el máximo permitido (150)."
  4. Corregí el dato y volvé a mandarlo: ahora devuelve 200.

    “Los datos inválidos nunca llegan a la base: Laravel los frena antes, en las clases de app/Http/Requests.”

Otros errores para mostrar si te lo piden (todos dan 422):

PUT /api/canchas/1{"estado": "rota"}El campo estado tiene que ser uno de estos valores: activa, inactiva.

Y otros códigos: PUT /api/clubs/999 con datos válidos da 404 “Club no encontrado”; POST /api/login con contraseña mala da 401 “Credenciales incorrectas”.

9. Borrar el club · 30 s

  1. DELETE /api/clubs/{id} con el mismo id. Devuelve 200: “Club eliminado correctamente”.
  2. GET /api/clubs/{id} otra vez: ahora da 404 “No se encontró el recurso pedido.”

    “Así quedó el ciclo completo: crear, editar, validar y borrar, todo protegido con el token.”

10. Cerrar sesión · 1 min

  1. Autenticación → POST /api/logout → Try it out → Execute. Devuelve 200: “Sesión cerrada correctamente”.
  2. Sin tocar Authorize, ejecutá GET /api/user: ahora da 401, aunque Swagger sigue mandando el mismo token.

    “El logout borra el token en el servidor. Aunque alguien lo haya copiado, ya no sirve.”

11. Reservas con cupo (opcional) · 1 min

  1. Explicá la regla del negocio: una reserva completa ocupa el turno entero; las reservas individuales suman jugadores hasta completar el cupo, y ahí el turno pasa a ocupado.
  2. Si un turno ya está ocupado, POST /api/reservas devuelve 409: “El turno ya no está disponible”. Si no alcanza el cupo: “No hay cupo suficiente en este turno”.
  3. Al cancelar una reserva (DELETE /api/reservas/{id}) el turno se libera si vuelve a haber lugar.

12. Cierre · 30 s

  1. Pasá a la pestaña del front, http://localhost:4200: clubes → club → cancha → turnos.

    “La página usa exactamente esta API. Lo que vimos en Swagger es lo que consume el front.”

Cómo interactúa la API

Cada vez que tocás Execute, Swagger hace un pedido HTTP real. Debajo del botón muestra todo lo que viaja y vuelve:

  • Curl: el pedido completo como comando. Se ven el método, la URL y los encabezados: accept: application/json, Authorization: Bearer ... y Content-Type: application/json, más el cuerpo con -d.
  • Request URL: la dirección exacta, con los filtros si los hay (por ejemplo /api/turnos?cancha_id=1&fecha=2026-09-04).
  • Server response: el código, el cuerpo en JSON y los encabezados de respuesta.

El recorrido de un pedido (por ejemplo, PUT /api/clubs/5)

  1. Ruta: Laravel busca en routes/api.php qué controlador atiende PUT /api/clubs/{id}. Si no existe la ruta → 404 “La ruta pedida no existe.”
  2. Autenticación: el middleware auth:sanctum revisa el token del encabezado Authorization. Si falta o no es válido → 401.
  3. Validación: la clase ClubRequest (en app/Http/Requests) revisa los datos. Si algo está mal → 422 con un mensaje por campo, y el pedido no sigue.
  4. Controlador: ClubController@update busca el club. Si no existe → 404 “Club no encontrado”.
  5. Base de datos: Eloquent guarda los cambios en MySQL (tabla clubs).
  6. Respuesta: la API devuelve JSON con el código 200 y el club actualizado.

“El front hace exactamente estos mismos pedidos. Swagger nos deja verlos y probarlos sin escribir código.”

Cuidados en vivo

Si algo da 401 después de Authorize, revisá que hayas pegado el token completo, incluido el número y la barra del principio. Si ya hiciste logout, volvé a hacer login y pegá el token nuevo.

Usá un club creado en la demo para editar y borrar, no uno de los que vienen cargados, así no cambiás los datos de prueba.

El ejemplo de POST /api/turnos sirve una sola vez. La segunda vez da 422 “Ya existe un turno en esa cancha para esa fecha y hora de inicio”. Si querés crear otro, cambiá la hora.

Si Execute queda girando unos segundos, es normal en la lista de turnos: calcula el cupo de cada uno.

Preguntas que te pueden hacer

¿Cómo se documenta un endpoint?

Con un atributo de PHP arriba del método del controlador. Por ejemplo, #[OA\Get(path: '/api/clubs', tags: ['Clubes'], ...)]. La parte general (título, servidor y esquema de seguridad) está en backend/app/Swagger/OpenApi.php.

¿Cómo se actualiza la documentación?

Después de cambiar los atributos, en la carpeta backend se corre php artisan l5-swagger:generate. Eso vuelve a generar storage/api-docs/api-docs.json, que es lo que lee la página.

¿Qué librerías usan?

L5-Swagger (darkaonline/l5-swagger) integra Swagger UI con Laravel, y swagger-php (zircote/swagger-php) lee los atributos y arma el archivo OpenAPI.

¿El candado de Swagger es lo que protege la ruta?

No. El candado solo indica que hace falta un token y permite enviarlo con Authorize. La protección real es el middleware auth:sanctum en routes/api.php.

¿Qué es Sanctum y cómo funciona el token?

Es el sistema de autenticación de Laravel para APIs. En el login se crea un token personal que se guarda en la tabla personal_access_tokens. El cliente lo manda en cada pedido como Authorization: Bearer <token>, y Sanctum identifica al usuario con él.

¿Por qué el front y Swagger tienen distinto puerto?

Porque son dos programas: Angular corre en el 4200 y Laravel en el 8000. Swagger documenta la API, así que está en Laravel. En desarrollo, el front manda todo lo que empieza con /api al 8000 mediante un proxy (frontend/proxy.conf.json).

¿Dónde está la validación de los datos?

En backend/app/Http/Requests: una clase por recurso (ClubRequest, CanchaRequest, TurnoRequest, ReservaRequest, JugadorAnotadoRequest) con las reglas, y ApiRequest con los mensajes en español. El controlador las recibe como parámetro y Laravel valida antes de entrar al método.

¿Por qué 422 y no 400?

422 (Unprocessable Content) indica que el pedido está bien formado pero los datos no cumplen las reglas. Es el código que usa Laravel para los errores de validación.

¿Qué hace el logout?

Borra de la tabla personal_access_tokens el token con el que se hizo el pedido. Desde ese momento ese token devuelve 401. Las sesiones en otros dispositivos siguen activas porque usan otros tokens.

¿Qué falta hacer?

Usar roles para que solo los administradores puedan crear clubes y canchas, y tomar el usuario de la reserva desde el token en vez de recibir usuario_id en el cuerpo.
